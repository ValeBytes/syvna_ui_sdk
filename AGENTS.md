# syvna_ui_sdk: Agent Guide

`@syvna/ui`, the components every Syvna app is built from, and the docs site that shows them. Private; apps install it as a package.

```
packages/ui/          @syvna/ui
  src/components/     the components (React + Tailwind 4), one file per family
  src/index.ts        what the package exports
  src/theme.css       GENERATED: the tokens as Tailwind values + @source for the components
  src/tokens.css      GENERATED: the token values, light and dark
  tokens.json         THE look: every colour (per theme), face, radius, shadow
  catalogue.json      GENERATED: every component, its summary and props, from the source
  docs/<Name>.md      each component's guide: when and how to use it
  scripts/            build.mjs (tokens, catalogue, canvas bundle), catalogue.mjs, registry.mjs, canvas tooling
  registry/           GENERATED by registry.mjs: one copy-in item per source file (index.json, r/<item>.json)
packages/cli/         syvna-ui: copies components into an app (init, add, list), like shadcn's add
packages/mcp/         the MCP server agents use to find components, read props and guides, check code
apps/docs/            the docs site (Next.js 16), localhost:4500; serves the registry at /r/
  registry/           each component's playground: controls, preview, code
  registry/meta.ts    the components in order, by group and kit (dashboard, website or agent)
  components/look.tsx the testing bar: device width (phone 390, tablet 820, laptop 1280, fit), theme, brand, and corners, font, text size, line spacing, text colour, density
  components/templates/  the template app (a shop): data.tsx, screens.tsx, frame.tsx; routes app/templates/
```

## Commands

| Command | What |
|---|---|
| `npm install` | Install the workspace (one `node_modules` at the root) |
| `npm run dev` | Build the tokens and catalogue, then the docs on :4500 |
| `npm run build -w @syvna/ui` | Regenerate theme.css, tokens.css and catalogue.json |
| `npm run typecheck` | Both packages |
| `npm run registry` | Rebuild the catalogue and the copy-in registry (also copied to apps/docs/public/r) |
| `npm run canvas` | The design-system Artifact canvas (see packages/ui/scripts/canvas.mjs) |

## Rules for components

- **Tokens only.** Every colour, radius, shadow, face and text size is a token class: `bg-surface`, `text-ink-3`, `border-line`, `rounded-lg`, `shadow-1`, `font-display`, `text-body`. Text sizes are the type styles in tokens.json (`text-caption`, `text-small`, `text-label`, `text-body`, `text-subtitle`, `text-title`, `text-heading`, `text-stat`, `text-display`), never `text-sm` or `text-[15px]`, so a design's type scale reaches every component. Never raw hex, never Tailwind's palette (`bg-gray-100`), never `dark:`: light and dark come from the tokens, so a component that uses only tokens works in both.
- **Statuses** go through `toneText` / `toneSoft` / `toneFill` in `src/cx.ts`, so a tone means the same everywhere.
- **`className` last, through `cn()`**, so a class an app passes wins over the component's own.
- **Every prop has a `/** comment */`** saying what it's for, with an example. The catalogue, the docs' props table and agents building apps all read these; a prop without one shows up blank everywhere.
- **The component's own doc comment** is its one-line summary in the catalogue.
- Interactive components (state, effects, events of their own) start with `"use client"`, so server pages can import them.
- Keyboard and screen readers: focus ring via `focusRing`, real buttons and links, `aria-*` where the role isn't obvious. Respect `motion-reduce`.
- Works on React 18 and 19: `forwardRef` for refs, no `use()`.

## Rules for screens (and for agents building them)

- **No page titles.** Breadcrumbs in the Topbar say where you are; screens start with their content.
- **No row of buttons on its own.** A screen's actions sit on a line that already exists: the tab row (`Tabs actions`), the filter row (`FilterBar actions`), a card's header (`Card actions`), or, for the one action that matters everywhere, the Topbar (`Topbar actions`). The Orders and Products templates show it. `check_code` in the MCP server flags the lone row.

## Adding a component

1. Write it in `packages/ui/src/components/`, export it and its `<Name>Props` from `src/index.ts`.
2. Write `packages/ui/docs/<Name>.md`: what it's for, when to use something else, the words to use.
3. Add its playground to `apps/docs/registry/` (controls, preview, code) and its name to `registry/meta.ts`.
4. `npm run registry`, then check its page in both themes (the playground's **Both**). The registry and the MCP server pick it up from the catalogue.

Changing a token: edit `tokens.json`, then `npm run build -w @syvna/ui`. Never edit the generated files.

## Three kits

The docs sidebar has three tabs; `registry/meta.ts` says which kit each group is in.

- **Dashboard**: app screens. Shell, actions (Button in 13 looks, ButtonGroup, SplitButton, ToggleButton, CopyButton), forms (Input in 15 looks with clear/counter/copy/add-ons, TagInput, NumberInput, CurrencyInput, DateRangePicker, Slider, InlineEdit, KeyValueEditor, ApiKeyField), data, table tools (BulkActionBar, ColumnSettings, SavedViews, TransferList, TreeView), layout (Accordion, Stepper), feedback (Banner) and the workspace (NotificationCenter, AuditLog, PermissionMatrix, InviteMembers, UsageMeter, PlanSummary, SetupChecklist, SaveBar, ConfirmByTyping, ApprovalCard).
- **Website**: landing pages and shops, in `site.tsx`, `hero.tsx` (21 variants), `site-header.tsx` (21), `pricing.tsx` (21) and `shop.tsx`. They size themselves by their own width (`@container`); links that act like buttons use `siteAction(variant, size)`. Website templates are at `/sites`.
- **Agent**: talking with AI agents. `chat.tsx` (Conversation, Message, PromptInput, Suggestions, Thinking, Confirmation, Questionnaire, VariantChooser, ModelSelector, ContextMeter), `trace.tsx` (Trace, TraceStep and the shapes built on it: Plan, TaskList, ToolCall, Reasoning, Subagent, Sources, InlineCitation, Checkpoint) and `dev.tsx` (CodeBlock, Terminal, StackTrace, TestResults, FileTree). The Conversation page runs a whole simulated chat. Terminal is dark in both themes on purpose; it's the one place raw colours are allowed.

**VariantChooser** is how an agent answers "I don't like this field": live previews of other looks in the chat, a dialog to compare them all, and the pick sent back. Build its options from the component's variants (`get_variants` in the MCP server).

## Palettes

Colour comes from roles, not colours, so an app can be any palette, not just light or dark: `brand` (the main action), `accent` (what's selected or in progress), `ink-heading` (titles, big numbers), `chrome-*` (the sidebar), `bar` (the top bar), greys, and `chart-1…6`. `src/palette.ts` makes all of them, light and dark, from a few seeds (`createPalette`), with 12 ready-made palettes (`palettePresets`); `PaletteStyle` applies one. A sidebar gets the chrome through `chrome-scope`, which re-points the ordinary token classes inside it.

- Use the roles in components: `bg-accent` for a selected state, `text-ink-heading` for a title. A missing role is a missing token, not a hex colour.
- `tokens.json`'s values are the Neutral palette; change the generator, not the tokens, to change how palettes are made, and keep its contrast checks passing (all presets, both modes).
- The colour guide for people and agents is `docs/PaletteStyle.md`.

## Copying components into an app

Apps can take only what they use instead of the whole package:

```
npx syvna-ui init                  # syvna.json, the core files (cx.ts, theme.css, tokens.css), the CSS imports
npx syvna-ui add DateRangePicker   # that file and every file it needs, in the same layout
npx syvna-ui list date             # what's in the registry
```

Items are one per source file, so imports between them work unchanged once copied; `index.ts` in the target re-exports what's been added. The registry is `packages/ui/registry` (served by the docs at `/r`); set `SYVNA_REGISTRY` to another URL and `SYVNA_REGISTRY_TOKEN` for a private one. Keep files small and their imports few: a file that imports another kit (a dashboard file importing `site`) drags that kit into every app that adds it.

## Versions and releases

One version for the library, the CLI and the MCP server (the root `package.json`), released as a git tag `vX.Y.Z`. The registry is committed, so an app reads it at a tag (`raw.githubusercontent.com/ValeBytes/syvna_ui_sdk/v0.2.0/packages/ui/registry`); `syvna.json` in the app records which release it's on, and `npx syvna-ui upgrade` moves it on, keeping files the app has changed.

- **As you work**, write what changed under **Unreleased** in `CHANGELOG.md`: Added, Changed (with what apps must do), Fixed. Renaming or removing a prop, changing a default or renaming a token is a breaking change: say so.
- **patch** for fixes, **minor** for anything new (and, before 1.0, breaking changes called out under Changed), **major** after 1.0 for anything apps must change.
- **Release**: commit everything, `npm run release -- minor` (it checks, bumps every package, rebuilds the registry, commits and tags), then `git push origin main --follow-tags`. The Release workflow publishes the notes and the registry for the tag.
- **CI** fails when `catalogue.json` or the registry is out of date: run `npm run registry` and commit them.

## The MCP server

`packages/mcp/server.mjs` (registered in `.mcp.json`) lets an agent use the library without reading all of it: `list_components` (by kit or words), `search_components` (plain-language needs to components and variants), `get_component` (props, guide, import and add command), `get_variants`, `get_tokens`, `add_command`, and `check_code` (unknown components and props, wrong variant values, raw colours, `text-sm`, `dark:`, page titles). It reads the generated catalogue, guides and registry, so run `npm run registry` after changing components. Try a tool from the shell: `node packages/mcp/server.mjs call search_components '{"query":"pick a period"}'`.

## Sidebars

`SideNav` takes the app's screens as data (`groups`) and draws one of 21 `variant`s; the list is `sideNavVariants`. A new sidebar type is a new case in `src/components/sidenav.tsx` and a name in that list; it then shows in the SideNav playground and in every template. `Sidebar` + `NavSection` + `NavItem` stay for sidebars built by hand.

## Templates

`/templates/<screen>` in the docs: a whole shop (dashboard, orders as a list or a drag-and-drop board, customers with filters and pages, a customer's own page, inbox, products, settings, onboarding, an empty new shop, sign in) built only from the components, with ⌘K search and toasts, with every sidebar type and the look controls. Use them to check a change across real screens before shipping it.

## The docs site

Built with the library itself. Pages are server components; playgrounds are client. Example data is international (Lagos, Osaka, São Paulo, Hamburg) and formatted with a fixed `"en-US"` locale in the docs so the server and the browser render the same text; apps format for the reader's locale.
